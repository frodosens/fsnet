# 属性合批与容器增量

本轮在原有类型、权限、版本和提交机制之上，增加客户端显式合批，以及下行容器补丁。
普通属性赋值仍保持原有等待确认的语义，不暗中延迟发送。

## 客户端一次提交多次修改

```lua
runtime.start(function()
    local player=Player:watch('alice')
    player:batch(function(draft)
        draft.items:add({id='potion',count=1})
        draft.items:add({id='sword',count=1})
        draft.tasks['daily.1']={progress=0,done=false}
        draft.tasks['daily.1'].progress=10
        draft.tags:add('questing')
    end)
    -- 到这里，整批已获得服务端确认。
end)
```

前提：这些顶层属性显式允许 `client='rw'`，调用者仍须是 owner，并通过服务端业务校验。
背包/奖励默认保持服务端写权限；是否接受客户端提案由业务决定，合批不授予额外权限。

- 回调收到独立的受管草稿，支持现有整值、字段、list/map/set 写法；回调读取草稿可看到自己的修改。
- 回调期间原确认副本不变。结束后仅收集最终变化的顶层属性，发送一次 write、执行一次 `validate_write` 和一次 CAS 提交。
- 同一元素反复修改仅提交最终值；添加后又删除、最终没有任何变化时，不发送 write。
- 草稿沿用起始确认版本。服务端若已推进版本，整批拒绝，不静默覆盖、自动合并或自动重试。
- 回调抛出错误时丢弃草稿；服务端拒绝也不修改确认副本。超时仍可能意味着服务端已提交，不能据此重新生成一批不同输入。
- 回调必须同步完成，不允许网络调用、sleep、主动 yield、嵌套 batch 或修改其他对象。禁止外部操作的尝试即使被 pcall 捕获，也会使整批失败；指令和内存预算继续生效。
- 回调结束后草稿及其字段视图失效。不得把它们保留为另一个长期状态对象。
- 只支持同一个确认副本，且非空提交必须来自可让出的异步任务。不是跨实体事务，也不直接用于服务端请求对象或预测状态。

第二个参数支持原有 write 选项：`timeout_ms`、`request_id`、`expected_revision`；显式版本必须等于草稿起始版本。
需要重试时，保存同一份确定的提案与请求 ID；不要把重新执行回调当成无条件安全重试。

```lua
player:batch(function(draft)
    for i=1,16 do draft.items[i].count=2 end
end,{timeout_ms=3000,request_id='inventory-edit-42'})
```

服务端原本就会将**一个实体方法内**的多次修改放在一次 CAS 中提交，并广播最终状态。
例如一次奖励 RPC 里循环添加 16 个 item，即已合并存储和发布；不需要对服务端对象再调用 `:batch()`。
多个独立 RPC 不会自动跨帧合并，以免改变确认、版本冲突和业务操作顺序。

## 服务端广播容器补丁

对每个订阅者最后成功发送的图像与新确认图像计算差量：

- map：键的新增/替换/删除，仅发送变化的键及新值。结构体值仍按整个元素替换。
- list、set、固定数组：保留共同前缀与后缀，发送一次连续区间 splice（索引、删除数量、新元素）。追加、删除或单点替换无需重发整个容器。
- 标量、固定结构等仍按属性替换；嵌套容器以发生变化的顶层容器元素为单位，不发送任意深度路径补丁。
- 计算完整记录的大小，补丁严格更小时才使用；密集/分散修改或超过 256 个编辑时回退整属性。
- 一个更新中可同时包含普通属性替换和多个容器编辑。首次订阅、重新获取快照、持久化仍使用完整 FSA1 图像。

补丁使用显式 **FSA2** 格式；FSA1 的既有记录保持可读。当前没有旧客户端能力协商，
启用本版本复制服务时需一起升级客户端和离线读取工具；不认识 FSA2 的旧读端会拒绝该记录。
客户端写提案仍为 FSA1 最终属性值，FSA2 仅用于下行，服务端明确拒绝将其作为写提案。

接收端先验证版本、所有补丁与合并后图像，再提交副本；缺版本、非法类型、越界 splice、
删除不存在的 map 键、容量/字节/节点超限均不部分生效。ACL/AOI、权限撤销、租约、代数及背压检查保持原有路径。
补丁是最终状态差量，不是业务操作日志，不保证逐条重放服务端中间的 add/remove 动作。

## 性能与验证

[测量结果与复现](CONTAINER_BATCHING_PERFORMANCE.md)，[原始样本](benchmarks/container-batching-2026-10-23.json)。

`fsnet-patches` 覆盖混合替换/补丁、稀疏/密集回退、截断、非法索引/类型、失败不部分发布、
合并图像节点限制和固定随机种子的 600 轮增删改重放。
`fsnet-containers` 验证 batch 一次提交、多属性同一版本、确认/草稿分离、取消、禁止网络/等待、
validator 拒绝、无变化不发、字段视图失效、owner/AOI、预测，以及多次草稿回收。
交付的 [结构属性客户端](../examples/lua/client/structured_entity.lua) 与独立进程测试也覆盖四次赋值一次提交。

本轮没有消除所有复制：构造草稿、提案和副本预算校验仍有图像/容器遍历；服务端仍持久化完整实体记录。
上行合批提案仍包含变化容器的最终全值；没有上行操作压缩、跨实体帧合包、共享观察者投影缓存或数值量化。
