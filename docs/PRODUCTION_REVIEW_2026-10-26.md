## P1：相关能力上线前修复

### R01：未授权订阅先激活实体，之后才拒绝

位置：`src/attribute_replication.cpp:98`、`:103`、`:110`。
有效全局 ID 跳过权限预检查，`read_attributes` 会先取得实体并执行激活，再在完成回调中检查可见性。
调用者知道有效 EntityId 和类型、且能访问订阅入口时，即使既不是 owner 也不是观察者，仍能触发该路径。

实测订阅返回 `rejected(5)`，但持久激活计数从 1 变成 2，实体从 inactive 变为 active。
没有读到私有属性；影响是未授权生命周期执行、租约/驻留资源占用，以及 hook 可能产生的外部副作用。
`src/client_gateway.cpp:68` 至 `:77` 的 restore 也静态确认有同样的先读取、后授权顺序，归为同一根因。

建议：提供不激活实体的可信元数据/权限查询，或让读取入口携带调用身份，在生命周期前完成授权；激活后的权限复核仍需保留。
验收应覆盖非 owner、未 show、卸载实体、错误类型及 restore，断言拒绝时生命周期和状态均未变化。

### R02：同一物理连接换逻辑身份后，Gateway 仍转发旧私有更新

位置：`src/client_gateway.cpp:132`、`:144`、`:314`、`:435`。
新请求会比较 ConnectionRef，但通知转发和定期检查依赖的 `authenticated` 只比较角色与 subject。

明确前提：**可信的自定义 identity adapter 在同一物理 peer、同一 subject 下更换 ConnectionRef**。
默认交付启动器本身不做这种换绑，不能把本问题写成通用 mTLS 或角色绕过。
实测换绑后不发送任何新客户端请求，旧会话与订阅仍在，客户端收到仅旧 owner 可见的 `secret=2`。

建议：每个身份复核边界统一比较完整逻辑连接，变化时撤销旧委托、订阅与未完成请求；迟到结果也应拒绝转发。
验收需分别覆盖请求、通知、空闲轮询和异步结果返回时换绑。

### R03：持续可读网络流量能让一次 Node::poll 长时间不返回

位置：`src/node.cpp:91` 至 `:98`；启动器调用顺序见 `examples/server/service.cpp:83`、`:106`。
非阻塞驱动直接调用无工作量/时间上限的 `io_context::poll()`，回调持续产生就绪工作时不保证让出主循环。

合法握手后的一个本地 peer 持续发送小型通知，两秒流量下，三次观察的最长单次 poll 分别为
1737.89、1874.12、2261.53 ms。这是明文 loopback 机制复现，**不是生产 mTLS 吞吐预测**。
Gateway 前端授权仅检查证书映射，已获准客户端可发送通知；帧大小、总内存和在途 RPC 限制不能代替通知速率及每轮工作预算。

后果：同线程 Lua、实体 tick、计时器、后端网络和停机信号处理被延后，不能仅以队列有界宣称实时性有保障。
建议：每次 poll 采用事件数或时间预算，加入连接/通知的速率与公平调度；压测时同时记录主循环最大停顿和业务尾延迟。

### R04：Lua GC 终结器可以卡住 VM 停止和析构

位置：`src/lua_engine.cpp:1579`、`:1698`，初始化失败清理也直接调用 `lua_close`（`:1575`）。
协程执行与取消已有预算，但主 Lua state 的终结过程没有同等约束。

探针加载带循环 `__gc` 的普通 Lua 表，配置 task_timeout=10ms、每次恢复指令数=1000。
加载成功，调用 stop 后进入 `GC_ENTER`，外部两秒截止时仍未返回；未出现 `STOP_OK`。
这会使部署文档中的有界退出无法完全依赖进程内 drain。

建议：明确并实现关闭/GC 时是否允许执行用户终结代码，以及不可让出边界的预算策略；不要破坏原生对象必须执行的资源释放。
验收需要覆盖 stop、析构、加载失败和 GC。这里审查的是可信业务脚本的故障约束，不是声称 VM 应隔离敌对代码。

### R05：Lua 属性展开和临时深复制在内存计费之前发生

位置：`src/lua_engine.cpp:299`、`:335`、`:714` 至 `:719`、`:791`；`src/entity_schema.cpp:118`。
Lua 表先展开成原生属性图，重复引用的字符串逐项复制；随后构造 mutation 和 projected 图继续深复制。
最终 wire 大小检查和 `reserve_external` 都发生在这些分配之后。

实测仅配置 2 MiB ScriptLimits，4×256 个元素引用同一个 64 KiB Lua 字符串，展开后约 64 MiB 原生字符串数据。
请求最终返回 `overloaded(6)` 且没有发布候选状态，但进程 RSS 从约 9 MiB 升至 **约 201 MiB**，VM 计费仍约 0.51 MiB。

单次转换仍受 4096 节点、深度 8、容器 256 项、单字符串 64 KiB 等限制，不能称为无限展开。
问题是多份原生临时图的峰值不受配置的 VM 内存限额控制，可能造成大幅停顿或进程 OOM。
建议展开时累计实际字节、每次分配前预留临时额度并用 RAII 归还；先验证图预算，再构造 mutation，减少中间深复制。

### R06：PostgreSQL 网络黑洞能阻塞存储线程和 stop/join

位置：`src/postgres_database.cpp:27`、`:32`、`:83`；`src/async_database.cpp:31`、`:40`。
libpq 查询使用阻塞接口，服务器 statement_timeout/lock_timeout 和连接超时并不限制连接建立后的客户端网络等待。
AsyncDatabase 停止则直接等待 worker 退出。

实测先通过本地代理连接真实 PostgreSQL，再让代理丢弃后续流量。操作开始后进入 stop，**7 秒仍未返回**，由外部截止清理。
代码没有提供覆盖此等待的应用期限，所以不能以五秒 SQL 超时推导整个存储调用或退出有界。
本问题属于已有故障边界的再次确认；不声称本次发现了新的数据库提交丢失。

建议：使用有 socket 等待期限的非阻塞 libpq 状态机、可取消操作和明确的有界关闭合同。
写入结果不明时必须保留“可能已提交”的语义，不能为了恢复连接盲目重放写操作。
验收应含连接成功后的黑洞、半开、恢复和停机，不只测试拒绝连接或数据库返回 SQL 错误。

### R07：空属性 rebuildable 实体在正常连续请求中丢失去重凭据

位置：`src/entity_host.cpp:391`、`:429` 至 `:430`、`:622` 至 `:624`。
缓存 fence 是否有效被绑定到 transient 是否非空；空属性实体没有 transient，下一次调用被当作失去驻留状态，清空 receipts。

同一实体、同一 owner、没有重启/迁移/失去租约，相同 request_id 连续调用：
durable 对照组执行 1 次并重放 1 次；rebuildable 组执行 **2 次、重放 0 次**。
这不是文档所述的卸载/接管后可重建状态丢失，而是当前驻留期间的重试语义错误。

建议独立记录驻留/fence 有效性，不能以“有无业务属性”判断实例是否仍驻留。
验收需含空 schema、有属性、续租和真正卸载后的区别；业务幂等仍有必要，但不能代替框架回执合同。

## 设计判断与容量边界

### 值得保留的设计

- Node 是服务载体，EntityId 是稳定业务身份；逻辑 ConnectionRef 与实体 owner 分开，迁移无需更换客户端引用。
- 客户端/服务端共用 AttributeValue、schema、字段 patch 和差量生成/应用，避免两套同步协议各自演化。
- 单实体 mailbox、单记录 CAS、lease/fence 和提交后回复，为并发与接管提供清晰边界。
- outbox/inbox 把已接受命令及去重状态纳入持久记录，计时器使用可序列化方法/参数，而不是保存闭包。
- 确认状态、预测状态和回放副作用分离，符合客户端预测的基本要求。

这些机制的方向合理，但端到端性质仍需每条入口共同维持。
本轮发现的授权时序、逻辑连接撤销和停机预算缺口，说明局部组件有检查并不等于组合以后仍满足合同。
后续应继续把身份比较、预算计费、完成/取消状态转换放到共同入口，避免各路径分别实现遗漏。

### C01：持久投递源索引是历史累计容量，不是当前 pending 容量

`src/entity_host.cpp:1060` 至 `:1068` 在源 CAS 前登记源，索引没有退休协议；
`src/entity_delivery.cpp:55` 至 `:74` 会加载并逐项读取源记录，各 owner 可重复扫描同一索引。
默认最多 4096 个源，硬上限可配置到 65536。文档已经披露该限制，因此这是生产规模限制，不作为隐藏缺陷重复报告。

将容量设为 2，两个源均完成投递并销毁后，索引仍含 2 项，第三个新源发送返回 overloaded，receiver 已收到前两笔且当前 pending=0。
所以持续创建/销毁发送者的游戏，即使没有积压，也最终达到累计容量；单纯增加上限还会增加历史扫描和全局索引 CAS 成本。
应设计保留去重安全性的源退休/分片/待发索引协议。完成 outbox 已有显式 forget，不能误写成所有投递记录都无法清理。
每源 FIFO 的头阻塞已明确披露；不可用目标会延迟该源后续命令，业务设计和容量验收必须考虑。

### C02：Memory 后端 CAS 拷贝整个存储表

`src/database.cpp:48` 至 `:56` 通过全表候选副本保证分配失败原子性，源码已注明开发后端。
256 B 记录的诊断样本中，100/500/2000 条记录做一次 CAS，分别分配 35756/177068/709096 B，204/1004/4004 次分配。
这不是只拷贝本条状态，不能用该后端推出生产持久存储性能，也不适合靠调大实体数直接扩容。

### C03：字段网络 patch 不等于字段级持久写

网络路径已有字段差量与合批，但实体提交仍编码并 CAS 整条权威记录，回执、投递和计时器也随记录增长。
因此减少 std::string 参数复制有价值，收益仍受整图构造、快照编码、CAS 和串行等待限制。
R05 的临时深复制优先于机械地把所有参数改成 string_view；异步保存的负载、存储结果、队列和回执需要拥有生命周期。
借用解析和公共 delta 已存在，应沿用；跨异步边界盲目借用会引入悬空引用。

本轮不新增吞吐结论，当前规模样本见 [实体性能报告](BENCHMARK_CURRENT_ENTITIES_2026-10-26.md)。
生产还需分别测持久 RPC、Gateway 往返、迁移中重试、投递积压、计时器追赶和长时间运行的 p95/p99/最大停顿。

| 多机 HA、网络分区、数据库主备/备份恢复、长稳与容量 SLO | 尚无完整目标环境验收 | 本机测试与一次 benchmark 不能替代 |

## 文档与交付一致性

`docs/ARCHITECTURE.md:3` 至 `:11` 仍写旧分支快照及“全局实体重构尚未实现”，
但当前实现与 `GLOBAL_ENTITIES.md` 已采用新模型。部分历史报告保存旧测试名与命令，导航虽标历史，
架构文件自身仍容易被误读为当前合同，应在后续修复中更新或明确标为历史，不应据它判断功能是否实现。

[部署手册](PRODUCTION.md) 已准确披露：目前没有把**全局实体 + mTLS + 双 owner 故障 + 负载**结合的一键验收。
TLS、全局流程、进程恢复分别通过，不能等价推导该组合已经通过。
当前数据格式仅 FER5/FTI2，旧存档不兼容是已确认的产品方向，不在本轮要求增加兼容层。

## 建议落地顺序和上线条件

1. 先修 R01–R07；以本文探针补充有明确断言的回归测试，断言授权拒绝无状态变化、身份撤销无迟到数据、poll/退出有界、预算前置、重试不重复。
2. 修 R08–R15，统一调用期限、完成/取消和 readiness 合同；更新当前架构文档。未启用的可选路径可明确禁用，但不能继续对其作已验收承诺。
3. 确认目标实体总量、活跃量、历史投递源/通道数、状态体积和定时器规模；设计 C01 的长期容量方案。
4. 使用真实 mTLS 与生产存储，完成双 owner + Gateway + 负载下的 kill/恢复/迁移/黑洞/断连验收，检查已接受消息不丢、去重、权限撤销和排空。
5. 在目标环境进行持续增长与故障恢复长稳、证书轮换、数据库故障转移、备份恢复及容量测试，明确 p99、恢复时限、告警和回滚标准。

完成代码修复只说明已知缺陷得到处理；生产准入还取决于实际启用能力及上述部署证据。
当前适合继续开发与受控验证，不建议以“全部代码已可随时生产使用”对外发布。
